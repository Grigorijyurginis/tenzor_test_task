# Анализ сложности SQL-запроса и перспективы оптимизации

## Запрос

```sql
WITH RECURSIVE ancestors AS (
    SELECT id, parent_id
    FROM org_units
    WHERE id = %(employee_id)s

    UNION ALL

    SELECT u.id, u.parent_id
    FROM org_units u
    JOIN ancestors a ON u.id = a.parent_id
),
root AS (
    SELECT id FROM ancestors WHERE parent_id IS NULL
),
descendants AS (
    SELECT id, parent_id, name, type
    FROM org_units
    WHERE id = (SELECT id FROM root)

    UNION ALL

    SELECT u.id, u.parent_id, u.name, u.type
    FROM org_units u
    JOIN descendants d ON u.parent_id = d.id
)
SELECT name
FROM descendants
WHERE type = 3
ORDER BY id;
```

Задача решена одним запросом (один round-trip к БД) вместо двух отдельных
(«найти офис» → «найти сотрудников офиса»), что даёт планировщику PostgreSQL
построить единый план и избежать лишнего сетевого обмена с приложением.

## Схема и индекс

### Внешний ключ: `DEFERRABLE INITIALLY DEFERRED`

`parent_id → org_units.id` в `sql/create_table.sql` объявлен как
`DEFERRABLE INITIALLY DEFERRED` — проверка ссылочной целостности откладывается до
`COMMIT`. Это нужно, потому что `loader.py` вставляет все записи одной транзакцией
через `executemany`, а входной JSON не гарантирует, что родитель идёт раньше
потомка: без отложенной проверки вставка потомка раньше ещё не вставленного
родителя падала бы с ошибкой FK, хотя итоговое состояние таблицы консистентно.

### Индекс на `parent_id`
```sql
CREATE TABLE IF NOT EXISTS org_units (
    id        INTEGER PRIMARY KEY,
    parent_id INTEGER REFERENCES org_units (id) DEFERRABLE INITIALLY DEFERRED,
    name      TEXT NOT NULL,
    type      SMALLINT NOT NULL CHECK (type IN (1, 2, 3))
);
CREATE INDEX IF NOT EXISTS idx_org_units_parent_id ON org_units (parent_id);
```

`id` уже индексирован как первичный ключ. Индекс на `parent_id` создаётся отдельно
для рекурсивных JOIN'ов запроса ниже — но, как показывает реальный план
выполнения на данных из задания (см. «Фактический план на текущих данных»),
при объёме таблицы в 19 строк планировщик PostgreSQL его **не использует**:
`Seq Scan` по всей (крошечной) таблице оказывается дешевле. Индекс создаётся
заранее не ради текущего объёма — см. «Зачем индекс нужен, даже если сейчас
не используется» ниже.

## Разбор сложности

Запрос состоит из двух логических фаз, выполняемых как рекурсивные CTE.

### Фаза 1 — подъём к офису (`ancestors`)

Якорь (`WHERE id = %(employee_id)s`) и `JOIN ... ON u.id = a.parent_id` на
каждой итерации ищут строку по `id` — точечный поиск по первичному ключу.
Число итераций равно глубине узла в дереве (для данных из задания — 2–3
уровня: сотрудник → отдел → офис, возможны и более глубокие цепочки вложенных
отделов, как «Отдел продаж → Отдел обслуживания корп. клиентов → Белова»).

Теоретическая сложность: **O(H)** точечных поисков по индексу PK, где H —
глубина узла относительно корня. Каждый поиск по B-tree индексу — O(log n) от
размера таблицы. Итого: **O(H · log n)**.

### Фаза 2 — спуск по поддереву офиса (`descendants`)

На каждой итерации выполняется `JOIN ... ON u.parent_id = d.id` — поиск всех
детей уже найденных на предыдущем шаге узлов. Итерации продолжаются, пока не
будет пройдено всё поддерево найденного офиса.

Теоретическая сложность **при использовании индекса на `parent_id`**:
**O(S · log n)**, где S — размер поддерева офиса (число офисов, отделов и
сотрудников внутри него), n — размер всей таблицы `org_units`. Именно ради
этой фазы и создан `idx_org_units_parent_id`.

### Итог (при условии, что планировщик использует индекс)

Суммарная сложность запроса — **O((H + S) · log n)**, то есть линейно зависит
от размера *конкретного офиса*, а не от размера всей таблицы (всех офисов
компании). Это ключевое свойство: даже если у компании тысячи офисов и
сотрудников, стоимость запроса определяется размером одного офиса, к которому
принадлежит запрошенный сотрудник. Оценка верна, только когда планировщик
реально выбирает `Index Scan` по `idx_org_units_parent_id` — при каком объёме
данных это происходит на практике, разобрано ниже.

Разбор:

- `Index Scan using org_units_pkey` в этом конкретном захвате — точечные
  поиски по `id` (якоря каждого CTE: `WHERE id = 3` и `WHERE id = $4`). Но
  **это не значит, что PK-поиск всегда использует индекс независимо от
  объёма таблицы** — см. ниже методологическую поправку: тот же якорный
  поиск при том же n=19, но со свежей статистикой (`ANALYZE`), тоже уходит
  в `Seq Scan`. Здесь план снят без предварительного `ANALYZE`.
- Оба рекурсивных JOIN'а — включая `Hash Cond: (u_1.parent_id = d.id)`, ради
  которого создан `idx_org_units_parent_id` — выполняются через `Hash Join`
  по `Seq Scan on org_units`. Сам индекс на `parent_id` в этом плане не
  используется ни разу.
- `Buffers: shared hit=12`, ни одного `read` — вся таблица целиком в кеше
  PostgreSQL, диск не читается вовсе. `Planning time: 0.633 ms` даже больше,
  чем `Execution time: 0.307 ms` — на таком объёме компиляция плана дороже
  его выполнения.
- Оценка планировщика по строкам сильно завышена (`rows=1160` против
  фактических `rows=19`) — известная особенность оценки стоимости
  рекурсивного члена CTE в PostgreSQL: заранее число итераций рекурсии не
  предсказать, и оптимизатор использует консервативную эвристику. На выбор
  плана это не повлияло (Seq Scan всё равно верно выбран самым дешёвым), но
  объясняет, почему цифры `cost=` здесь не стоит читать буквально.

**Методологическая поправка.** План выше снят в DataGrip сразу после загрузки
данных, без явного `ANALYZE org_units` — то есть на статистике, которую
PostgreSQL успел собрать сам (autovacuum/autoanalyze мог ещё не сработать).
Повторный прогон того же n=19, но с явным `ANALYZE` перед `EXPLAIN`, даёт
другую картину: `Seq Scan` вместо `Index Scan` даже для точечного поиска по
`id` (`Filter: (id = 3)`, `Rows Removed by Filter: 18`). Значит, выбор плана зависит от статистики так же, как и от
самого объёма данных — со свежей статистикой планировщик ещё увереннее
выбирает `Seq Scan` на таком маленьком n, потому что точно знает, что строк
всего 19. Все последующие синтетические прогоны (ниже) используют явный
`ANALYZE` перед каждым `EXPLAIN`, чтобы результаты были сопоставимы друг с
другом.

### Порог переключения на практике (синтетические данные)

Проверено экспериментально: добавлял синтетические офисы/отделы/сотрудников
(id вне диапазона реальных данных, не пересекаются) внутри транзакции с
`ROLLBACK` в конце — тем же приёмом, что и в интеграционном тесте
(`tests/test_queries.py`), реальные 19 строк не затрагивались. Перед каждым
`EXPLAIN` — явный `ANALYZE org_units`, запрос — тот же самый, `employee_id = 3`
(офис в Санкт-Петербурге, не меняется при добавлении синтетических офисов).

| n (всего строк) | Скан для `parent_id`-JOIN | Execution time |
|---|---|---|
| 19 (только реальные данные) | `Seq Scan` | 0.195 ms |
| 49 | `Seq Scan` | 0.209 ms |
| 109 | `Bitmap Index Scan` на `idx_org_units_parent_id` | 0.265 ms |
| 319 | `Bitmap Index Scan` на `idx_org_units_parent_id` | 0.175 ms |
| 30 019 | `Index Scan` на `idx_org_units_parent_id` | 0.096 ms |
| 300 019 | `Index Scan` на `idx_org_units_parent_id` | 0.124 ms |

Порог переключения для этого окружения — между 49 и 109 строками (уже не
«десятки тысяч», как предполагалось до эксперимента, а пара десятков —
планировщик PostgreSQL переключается на индекс намного раньше, чем можно было
бы ожидать интуитивно).

PostgreSQL проходит три стратегии по мере роста n:
1. **`Seq Scan`** — полное сканирование таблицы, дешевле индекса, пока таблица
   помещается в одну-две страницы.
2. **`Bitmap Index Scan` + `Bitmap Heap Scan`** — промежуточная стратегия:
   индекс строит битовую карту подходящих страниц кучи, затем страницы
   читаются одним проходом (не по одной, как в обычном Index Scan) —
   выгодна, когда через индекс проходит заметная (но не подавляющая) доля
   таблицы.
3. **`Index Scan`** — прямой обход B-tree с точечным чтением строк, выигрывает,
   когда искомых строк исчезающе мало относительно размера таблицы.

Ключевое наблюдение для сложности запроса: `Execution time` **не растёт** с
ростом n при переходе от 30 019 к 300 019 строкам (0.096 → 0.124 ms, в
пределах шума измерения) — офис в Санкт-Петербурге и его 6 узлов (H+S)
остаются той же фиксированной величиной независимо от того, сколько
синтетических офисов добавлено рядом. Это прямое эмпирическое подтверждение
**O((H + S) · log n)**: стоимость запроса определяется
размером конкретного офиса, а не размером всей таблицы, как только
планировщик использует `idx_org_units_parent_id`.

### Зачем индекс нужен, даже если сейчас не используется

Индекс создаётся при инициализации схемы (`sql/create_index.sql`, один раз в
`schema.init_schema`), а не добавляется по факту роста данных — по двум
причинам:

1. **Стоимость почти нулевая при таком объёме.** На 19 строках лишний индекс —
   несколько килобайт на диске и небольшие издержки на `INSERT`/`UPDATE`
   (в `loader.py` — `UPSERT`). Создать его сразу дешевле, чем отслеживать
   момент «пора добавить индекс» и накатывать миграцию отдельно в проде.
2. **Он определяет асимптотику, а не текущее поведение.** Без
   `idx_org_units_parent_id` деградация фазы 2 до `Seq Scan` была бы
   **постоянной при любом n** — O(S · n) вместо O(S · log n),
   независимо от размера таблицы. С индексом деградация — временная и
   объясняется исключительно тем, что при n = 19 планировщик считает Seq Scan
   дешевле. По мере роста таблицы стоимость `Seq Scan` (растёт линейно с n)
   в какой-то момент превысит стоимость `Index Scan` (растёт логарифмически),
   и планировщик сам переключится — без единой правки кода или SQL.

## Перспективы оптимизации при росте нагрузки/объёма данных

Текущая модель — **adjacency list** (родитель хранится прямо в строке) —
самая простая в реализации и достаточная, когда:
- дерево меняется редко (справочник орг. структуры, а не операционные данные);
- глубина дерева небольшая (единицы уровней);
- запросы "предок → всё поддерево" не выполняются в высоконагруженном hot path.

Если эти условия перестанут выполняться, есть более быстрые на чтение модели
хранения иерархий (все — ценой более дорогой записи):

### 1. Closure table (таблица транзитивного замыкания)

Отдельная таблица `org_unit_ancestors (ancestor_id, descendant_id, depth)`,
где для каждой пары "предок-потомок" (включая узел с самим собой) заранее
материализована строка.

- Выборка сотрудников офиса — **один обычный (не рекурсивный) JOIN** по индексу:
  `O(S · log n)` без рекурсии, при этом проще для оптимизатора.
- Стоимость: при добавлении/переносе узла нужно пересчитать O(глубина) строк
  замыкания; при переносе целого поддерева — O(глубина × размер поддерева).
- Оправдана, если чтения (запросы вида "весь офис по сотруднику") сильно
  преобладают над записями (переносами сотрудников/отделов).

### 2. Materialized path через расширение `ltree`

Каждому узлу хранится путь от корня, например `1.2.3` (офис.отдел.сотрудник),
тип `ltree`. Поиск поддерева — оператор `<@` с **GiST-индексом**, поиск предков —
разбор самого пути, без рекурсии.

- Плюсы: очень быстрые запросы "поддерево" и "путь до корня", не требует
  рекурсивных CTE вовсе.
- Минусы: при переносе узла в другое поддерево нужно обновить путь у него
  и у всех потомков (можно сделать одним `UPDATE ... WHERE path <@ old_path`).
- Хороший следующий шаг именно для этой задачи, если появятся частые запросы
  "все сотрудники офиса/отдела" при большом числе офисов и сотрудников.

### 3. Nested sets (lft/rgt)

Каждому узлу — пара чисел, задающая его положение при обходе дерева в глубину;
поддерево — это диапазон `lft/rgt`, выборка — один `BETWEEN` по индексу, без
рекурсии вообще.

- Плюсы: самое быстрое чтение поддерева.
- Минусы: вставка/перенос узла требует пересчёта `lft/rgt` у потенциально
  большого числа соседних строк — дорого при частых изменениях структуры.
  Обычно не рекомендуется для деревьев, которые часто редактируются.

## Рекомендация

Для решения задачи в текущем виде (справочник орг. структуры, десятки-сотни
записей, structure меняется нечасто) **adjacency list + рекурсивный CTE с
индексом по `parent_id`** — оптимальный баланс простоты кода, отсутствия
лишних таблиц и производительности. Если в будущем появится множество
одновременных запросов вида "все сотрудники офиса" на большом объёме данных —
первым шагом стоит рассмотреть **`ltree`**: он не требует поддерживать
отдельную таблицу замыкания, при этом убирает рекурсию из hot path.
